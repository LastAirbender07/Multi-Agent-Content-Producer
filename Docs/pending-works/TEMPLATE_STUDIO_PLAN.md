# Template Studio — No-Code Slide Type Creation

> **Status:** Planned — not yet implemented  
> **Created:** 2026-07-04  
> **Current implementation:** Adding slide types today requires writing TypeScript. The manual process is documented in `Docs/renderer/ADDING_A_SLIDE_TYPE.md`.

---

## The Problem with the Current Workflow

Creating a new slide type currently requires a developer to:
- Understand Fabric.js, the token system, and the two-pass layout pattern
- Write a TypeScript builder file and test it manually
- Update 4–6 files across frontend and backend (`contracts.py`, `index.ts`, `slideTemplates.ts`, `settings.py`, `system_prompts.py`, optionally `reorder.py`)
- Rebuild the renderer bundle and validate the output

This is fine for engineers. It is a barrier for everyone else — designers, content strategists, or power users who want to experiment with a new layout.

---

## The Vision

```
Design in editor → LLM evaluates → User refines → Register → Done
```

A new slide type can be created entirely within the editor UI — no code, no terminal, no PRs.

---

## The Proposed Workflow

### Phase 1 — Design (editor already supports this)

The editor already has everything needed for the design step:
- **Blank slide creation** — "New Slide" with any type
- **Drag-and-drop components** — Glass Card, Stat Block, Bullet List, Glow Blob, Accent Line, all 6 pill button styles, etc.
- **Component property editing** — move, resize, recolour any element
- **Save as template** — the "Saved" tab in the Templates panel persists the current slide

A designer uses these existing tools to build the target layout visually. No code required.

---

### Phase 2 — LLM Evaluation (new)

An **"Evaluate Layout"** button in the editor toolbar triggers an LLM analysis of the current canvas state. The LLM:

- Reads the Fabric.js object tree (every object has a `data.role` field set by `setData()`)
- Compares the layout against the existing builders for consistency
- Scores on: visual hierarchy, whitespace usage, typography scale, theme token compliance, brand bar presence
- Returns **suggestions only** — no automatic edits

Example output:
```
✅ Brand bar present
✅ Title uses theme font (Syne Bold)
⚠️  Body text colour is hardcoded #444444 — should use t.muted for theme compatibility
⚠️  No accent line — other content slides use createAccentLine for visual rhythm
❌  Text layout is fixed-position — needs calcTextHeight() two-pass pattern to avoid overflow
Score: 6/10 — functional but not theme-consistent
```

The user reviews the suggestions and adjusts the layout before proceeding. The LLM can be re-invoked after each round of edits.

---

### Phase 3 — Registration Workflow (new)

After the layout passes evaluation (score ≥ threshold, no ❌ items), a **"Register Template"** button opens a guided form:

| Field | Purpose |
|-------|---------|
| **Type name** | `checklist`, `timeline`, `comparison` — the string used in SlideType enum and canvas_template |
| **Description** | One sentence — used in the LLM content prompt and editor tile tooltip |
| **Tile label** | Short display name shown in the editor Slides tab |
| **Tile emoji + colour** | Visual identity for the tile card |
| **Image behaviour** | Does this type fetch images? Controls `content_no_image_slide_types` |
| **Starter content** | Sample title + body seeded when a user creates this type from the editor |

On confirmation, the system **automatically**:

1. Generates `frontend/utils/canvasTemplates/aurora_{type}.ts` from the canvas object tree — translates FabricObject positions and roles into TypeScript builder code using shared components (`makeText`, `createBrandBar`, etc.)
2. Adds two entries to `REGISTRY` in `index.ts` (aurora + lumina via `lw()`)
3. Adds metadata entry to `TEMPLATE_METADATA` in `slideTemplates.ts`
4. Adds the new value to `SlideType` enum in `contracts.py`
5. Updates `content_no_image_slide_types` in `settings.py` if applicable
6. Appends LLM generation rules to `system_prompts.py`
7. Rebuilds the renderer bundle (`node backend/renderer/build.mjs`)
8. Runs a quick render test (3 slides with placeholder content)

---

### Phase 4 — Validation

Before finalising, the system renders 3 test slides using the placeholder starter content and displays them in the editor side-by-side. The user confirms the output looks correct, then hits **"Confirm Registration"**.

The new slide type is now:
- Available in the editor's "Slides" tab immediately
- Generated by the LLM pipeline when content fits the type description
- Exported to PNG via the same Playwright path as all other types

## Technical Prerequisites

Everything this feature needs either already exists or has a clear build path:

| Capability | Status | Notes |
|-----------|--------|-------|
| Editor canvas object tree inspection | ✅ Exists | Every object has `data.role` via `setData()` |
| REGISTRY auto-discovery | ✅ Exists | `SLIDE_TYPES` already derives from REGISTRY keys |
| `inferTemplate()` fallback | ✅ Exists | No renderer dispatch changes needed |
| LLM API (Claude) | ✅ Exists | Already used throughout the pipeline |
| `render_slide_fabric()` | ✅ Exists | Used for the validation render test |
| `api.newSlide()` + `api.editSlide()` | ✅ Exists | Creates test slides in the editor |
| Canvas → TypeScript code generation | 🔲 New work | Translate FabricObject tree to builder code |
| File write API (backend) | 🔲 New work | Backend endpoint to write generated `.ts`, update `.py`, `.json` files |
| Bundle rebuild trigger | 🔲 New work | API call that runs `build.mjs` and returns result |

**The key new work** is the code-generation step: translating a Fabric.js canvas object tree into a TypeScript builder function. This is tractable because every canvas object has a `data.role` field that maps directly to a shared component (`createAccentLine`, `makeText`, `createBrandBar`, etc.) — the mapping is mostly mechanical.

---

## Scope Boundaries

**In scope:**
- Aurora theme builder generation (Lumina comes free via `lw()`)
- Single-layout types (no layout variants like `content-0/1/2/3`)
- Types that use `bullets` field (most new types will fit this)

**Out of scope for v1:**
- Multi-layout types (e.g. content has 5 layout variants driven by image aspect ratio)
- Types requiring new Slide schema fields not already in `contracts.py`
- Automated reorder placement (defaults to middle content zone, which is correct for most types)

---

## Why This Matters

The rendering engine consolidation (Phases 1–4) made it structurally cheap to add new slide types — one builder file, two registry lines. The Template Studio makes it **zero-code cheap** — and shifts the quality gate from "can the developer write Fabric.js correctly" to "does the LLM evaluate the layout as consistent."

This opens slide type creation to designers and content strategists. The architecture's registry-driven design was always pointing at this — the Template Studio is the natural next evolution.
